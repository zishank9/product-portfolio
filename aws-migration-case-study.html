Project Overview

Some properties had been provisioned in AWS regions that did not match their intended geographic or operational environment. Examples included Asia-Pacific properties placed outside their intended China environment, European properties hosted in US regions instead of EMEA, and properties assigned to one US East environment when another was required.

The initiative addressed these placement inconsistencies while supporting more balanced distribution of data and resource usage across US environments. Each move had to preserve the property's operational data and ensure that dependent services remained accessible in the destination environment.

Two connected migration tracks: Property data relocation using AWS Database Migration Service (DMS) and Java-based destination transformations; and IoT migration using Kura packages with destination-specific snapshot updates.

The Challenge

A property is more than a database record. Its data, application resources, and connected IoT configurations must remain consistent after relocation. A successful transfer was therefore not just about copying information: it was about making the property usable in its new region.

  • Regional placement: Move properties from incorrectly assigned environments into their intended region, including APAC-to-China, US-to-EMEA, and US East environment corrections.
  • Data integrity: Ensure required records and relationships were transferred and transformed appropriately for the destination.
  • Execution speed: Coordinate a migration process that could complete efficiently while minimizing operational disruption.
  • IoT continuity: Update region-dependent Kura snapshot configuration so connected resources referenced the destination environment.
  • Post-migration access: Validate that the relocated property's resources and expected functionality remained available.
Central delivery question: How do we move a live property's data and connected configuration to the correct environment without leaving records, references, or resources behind?

Two Migration Workstreams

The work required separate handling of application data and connected IoT configuration. Both needed to agree on the destination environment.

01

Property Data Migration

Source region → AWS DMS → destination region

Database records were transferred across regions. Java-based logic handled items that required transformation or destination-specific updates.

Validation focus: Required data present, expected relationships preserved, and destination resources accessible.

02

IoT Configuration Migration

Source Kura configuration → snapshot updates → destination environment

The IoT workstream used Kura packages and code that rewrote snapshot-file values to match the destination environment.

Validation focus: Destination-specific configuration applied and dependent IoT resources accessible.

How I supported execution

  1. Confirm placement: Establish source and destination regions for the affected properties.
  2. Align dependencies: Coordinate data, application, infrastructure, and IoT workstreams.
  3. Prepare migration: Follow up on DMS, Java transformations, Kura snapshot changes, and Rundeck execution needs.
  4. Validate the move: Review transferred data, updated configuration, and access to destination resources.
  5. Resolve gaps: Coordinate troubleshooting when data or dependent resources do not behave as expected.

What This Project Reinforced

  • Regional migration is a business and operational problem: Correct placement matters for how services and data are distributed.
  • Moving data is only one part of the job: Destination-specific transformations and connected configuration require equal attention.
  • Validation must cover usability: A successful transfer still needs checks that the destination's resources can be accessed.
  • Development planning and code reviews matter: Reviewing implementation decisions against migration requirements helped identify dependencies and potential gaps before execution.
  • Clear coordination reduces ambiguity: Database, development, DevOps, and IoT dependencies need a shared execution plan.
